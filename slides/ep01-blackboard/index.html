What is Embabel?

Spring AI gives you the HTTP call.
Embabel gives you the brain.

Spring AI is great at making a single call to an LLM — send a prompt, get a response. But it doesn't answer: in what order should I call things? Which model should I use for each step? What happens when a step fails?

LayerWhat it doesAnalogy
Spring AI HTTP client to OpenAI / Anthropic / Gemini Servlet API
Embabel Plans and sequences steps toward a goal automatically Spring MVC
Created by Rod Johnson — the same person who created the original Spring Framework. This is not a weekend project. It's on Maven Central, has 4.5k GitHub stars, and is growing fast.

Before We Start

What actually happens in one agent run?

Imagine a loan approval system. A user submits an application. Three things need to happen — credit check, risk assessment, final decision. In a normal Spring app you'd write the flow yourself. In Embabel, you don't.

Step 1
Credit Check
Takes LoanApplication → produces CreditScore
Step 2
Risk Assessment
Takes CreditScore → produces RiskAssessment
Step 3
Final Decision
Takes RiskAssessment → produces LoanDecision ✓
You never write: "first do step 1, then step 2, then step 3." You just declare what each step needs and what it produces. The planner figures out the sequence. This episode is about where the data lives between steps — the Blackboard.
What the code looks like

A complete agent — three annotations, zero flow control

This is the entire loan approval agent. No "first do step 1, then step 2" anywhere. Just three annotated methods:

@Agent(description = "Processes loan applications end to end") class LoanApprovalAgent { @Action // Step 1 fun evaluateCredit( application: LoanApplication, // reads this FROM blackboard ai: Ai ): CreditScore = // writes this TO blackboard ai.withDefaultLlm().createObject("Evaluate credit for ${application.applicantName}") @Action // Step 2 — runs after step 1 fun assessRisk( score: CreditScore // needs CreditScore → planner runs step 1 first ): RiskAssessment = RiskAssessment(score.score > 650, "Score based assessment") @AchievesGoal(description = "Produce a final loan decision") @Action // Step 3 — the finish line fun generateDecision( assessment: RiskAssessment, // needs RiskAssessment → planner runs step 2 first ai: Ai ): LoanDecision = // goal achieved when this hits the blackboard ai.withDefaultLlm().createObject("Generate decision based on: $assessment") }
@Agent marks the class. @Action marks each step. @AchievesGoal marks the finish line. The planner infers the sequence from parameter types — you write zero ordering logic.
Episode 01 — Concept 1 of 3

The Blackboard is the agent's shared memory

Every step in the agent run reads from and writes to one shared object — the Blackboard. Steps never pass data to each other directly. Everything goes through the board.

Real world analogy: A whiteboard in a meeting room. The credit team writes the score on it. The risk team reads it. The loan officer reads both and writes the final decision. Nobody hands documents directly — everything goes through the board.
Scope
One per agent run. Isolated. Never shared across runs.
Thread safety
All operations threadsafe. Multiple steps can run in parallel safely.
Immutability
Append-only. Objects are never deleted — only hidden from retrieval.
Concept 1 continued

Internally it's an ordered list. Last one wins.

After the loan agent runs, the Blackboard's objects list looks like this. Each step added one entry:

blackboard.objects — insertion order
[0]
LoanApplication
applicantName="Sumit", amount=500000
latest
[1]
CreditScore
score=750, rating="Good"
latest
[2]
RiskAssessment
approved=true, reason="Low risk"
latest

From the actual Blackboard.kt source code: fun <T> last(clazz: Class<T>): T? — always returns the last object of a type.

Concept 1 — Append only

Two objects, same type — last wins, old stays

If a fraud check re-evaluates and adds a new CreditScore, the old one isn't deleted. It's still there — but invisible to retrieval:

blackboard.objects after fraud check re-evaluation
[0]
LoanApplication
applicantName="Sumit", amount=500000
latest
[1]
CreditScore
score=750, rating="Good"
hidden
[2]
RiskAssessment
approved=true, reason="Low risk"
latest
[3]
CreditScore
score=690, rating="Fair"
latest
Why keep the old one? Audit trail. The full history of every run is preserved. You can always see what changed and when. The Blackboard never deletes.
Concept 2 of 3

The planner uses type names as strings, not classes

The planner doesn't import your domain classes. It reasons purely with string names. From the actual Blackboard.kt source:

// The planner asks: "does CreditScore exist on the blackboard?" // It passes a plain String — not Class<CreditScore> fun hasValue( variable: String, type: String, // ← just "CreditScore" dataDictionary: DataDictionary, ): Boolean // satisfiesType() resolves it — also handles inheritance fun satisfiesType(boundInstance: Any, type: String): Boolean { if (boundInstance::class.simpleName == type) return true val interfaces = findAllSupertypes(boundInstance::class.java) if (interfaces.any { it.simpleName == type }) return true return false }
Planning time → string names only. No real classes needed.
Execution time → real objects injected into your action parameters.
Concept 3 of 3

Actions never touch the Blackboard directly

You declare what you need as parameters and what you produce as return type. The framework handles all the reading and writing.

@Action fun evaluateCredit( application: LoanApplication, // framework reads this FROM blackboard ai: Ai // framework injects this (NOT from blackboard) ): CreditScore { // framework writes this TO blackboard return ai.withDefaultLlm().createObject( "Evaluate credit for ${application.applicantName}, amount: ${application.amount}" ) } // You never write these — the framework does it for you: // val app = blackboard.last(LoanApplication::class.java) // blackboard += creditScore
Key insight: If a parameter type doesn't exist on the blackboard yet, the planner finds which action produces it and runs that first — automatically. You write zero sequencing logic.
Summary — Episode 01

3 things to remember about the Blackboard

1
Append-only ordered list. Objects are never deleted. The last one of each type is the active one. Full history preserved as an audit trail.
2
The planner uses string type names. Decoupled from your classes. Real objects are only resolved at execution time when the action actually runs.
3
Actions never touch it directly. Declare parameters → framework reads. Return a value → framework writes. Sequence is inferred from your method signatures.
