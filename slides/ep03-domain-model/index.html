Domain Model

The data classes that flow through your agent. Where every agent starts.

Concept

Design the data first, then the actions.

In Embabel, your domain classes are the contract between actions. Each action reads one type from the Blackboard and produces another. The domain model is what flows through the pipeline.

Kotlin Concept

data class — Kotlin's version of Java records

Java (verbose)
public class CreditScore {
  private final int score;
  private final String rating;
  // constructor...
  // getters...
  // equals/hashCode...
  // toString...
} // ~40 lines
Kotlin (1 line)
data class CreditScore(
  val score: Int,
  val rating: String,
  val factors: List<String>
)

// equals ✓ hashCode ✓
// toString ✓ copy ✓
val = read-only after construction (like Java final). Every field in your domain classes should be val — immutable by default.
LLM Hints

Jackson annotations help the LLM fill in the fields

@JsonClassDescription("A loan application submitted by a customer") data class LoanApplication( @JsonPropertyDescription("Full name of the applicant") val applicantName: String, @JsonPropertyDescription("Loan amount requested in rupees") val amount: Int, @JsonPropertyDescription("Purpose: home, car, personal, business") val purpose: String, )
Embabel generates a JSON Schema from your data class and sends it to the LLM. These descriptions become part of that schema — they tell the LLM exactly what to put in each field.
Our Domain Model

4 classes. The entire agent lives in these.

LoanApplication
applicantName, amount, purpose
→ The starting input
CreditScore
score (300–900), rating, factors
→ Produced by credit check
RiskAssessment
approved, riskLevel, reason
→ Produced by risk check
LoanDecision
approved, message, nextSteps
→ The Goal — agent is done
Notice: no business logic, no methods, no service calls. Just data. Actions are separate. This separation is what makes the system testable and composable.
